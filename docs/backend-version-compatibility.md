# MoviePilot 后端版本兼容维护

## 规则

- 兼容按**精确版本**登记，登记表是 `MoviePilot-TV/Models/BackendCompatibility.swift` 中的 `BackendCompatibilityRegistry.current`。
- 登记标准：对照官方源码（后端标签及其 `version.py` 指定的配套 Web 版本），确认 TV 实际调用的接口、返回字段、权限和订阅写回没有受影响，即可登记。**不要求真实后端实测**；真实后端兼容测试（`docs/backend-compatibility-tests.md`）只是可选的补充手段。
- 未登记的版本不推断为兼容。App 只在后端版本低于最早登记版本、落在登记版本之间但未登记、高于最新登记版本或读不出版本号时提示；用户确认后，同一服务器的同一后端版本不再提示，新增登记也不会让已确认的版本重新弹窗。
- 提示不展开完整登记表。中间未登记版本的标题为“兼容性尚未验证”，正文用“已兼容的版本：X...Y”简写比当前版本高的最近已验证版本和最新已验证版本，两者相同时只显示一次。较新或无法识别的版本用同样格式简写最早与最新登记版本；省略号不表示中间所有版本均已验证。提示正文不再附加“仍可继续使用”。
- 版本号只识别官方稳定版本：三段数字加可选的正整数热修复后缀，例如 `v3.0.10 < v3.0.10-1 < v3.1.0`。beta 等其他后缀按“无法识别”处理。
- 已知缺陷的功能、版本范围与文案集中在 `BackendCapabilities.knownDefects`，入口和操作 Handler 统一通过 `capability(for:backendVersion:)` 判断。已知不可用版本在入口置灰并显示原因；未知版本放行，点击复用不额外刷新全局配置。
- 旧的“后端版本|最低版本”确认记录在读取时迁移为版本 ID，升级 App 不会重复提示已经确认的同一版本。
- 不按版本复制接口或模型。只有某个功能在确定的版本范围内有已证实的上游缺陷时，才按版本阻止该功能，规则见 `.agents/engineering-invariants.md` 的“已知缺陷版本门禁”。
- v2 与 v3 的媒体身份属于协议级差异（单值媒体键 → 成对参数），不适用上面的“不复制接口”条款：v2 请求形状集中在 `MoviePilot-TV/Services/BackendProtocol/MoviePilotV2/`，由 `BackendEndpointBuilding` 在 `APIService` 之外整体替换，业务代码不感知版本；删除该目录即可退出 v2 兼容，步骤见“v2 后端协议适配”。新增取值或新能力的可用性门禁（如新整理方式 `reflink`）按 `>= 目标版本` 在入口显隐，读不出或低于目标版本时不展示，可解析且 `>=` 目标版本（含热修复和尚未登记的更新版本）仍展示；这类门禁不做接口复制，也不适用缺陷门禁的“未知放行”。只在某个版本起才成立的新功能、新入口或提示，按同一文档的“新行为版本限制”处理：已解析的更低版本不得走这条新行为。破坏性副作用确认在版本缺失或无法解析时仍提示。

### v3.1.4 核对范围与边界

对照官方后端 [v3.1.2-1 → v3.1.4](https://github.com/jxxghp/MoviePilot/compare/v3.1.2-1...v3.1.4) 及各标签 `version.py` 指定的 Web [v3.1.2 → v3.1.4](https://github.com/jxxghp/MoviePilot-Frontend/compare/v3.1.2...v3.1.4)。Web 基准提交为 `f3699b154df93a52445a5ef6130535bcf57f22cf`，目标提交为 `23220e062d6d23c08b8be63271ffac3f6a06a085`。本次只新增目标精确版本 v3.1.4，不推断 v3.1.3 或未登记热修复版本兼容。

- **认证**：连续密码登录失败新增 `429` 和 `Retry-After`，异常包装仍为 `success:false`、本地化 `message`、`data:null`。TV 现有处理会显示错误、保留会话与保存的凭据，自动续期沿用已有退避；没有新增按 `Retry-After` 倒计时的 UI。明确密码拒绝、MFA、`/user/current` 失效信号和权限字段未变，MFA 仍仅提示不支持。CORS 调整不改变原生客户端的认证请求。
- **订阅**：schema、公共可写字段、分享/Fork、完整列表、查询和删除范围未变。识别源配置为 TMDB 时，后端会尝试将豆瓣、Bangumi 等非 TMDB 影视订阅转换为 TMDB 身份；失败时沿用原身份。暂停会在安全边界停止自动搜索和后续下载提交，显式手动补搜仍可执行且不恢复订阅。TV 继续按订阅业务 ID 操作并强制刷新，不自行改写身份或运行状态。
- **上游共同限制**：配套 Web 的详情和卡片分季状态仍用当前媒体的 `media_source + media_id` 精确匹配 `/subscribe/`。身份转换后，从原来源页面进入时可能看不到对应分季的已订阅状态；媒体级查询的标题/年份回退也没有扩展为删除合同。TV 保留现有匹配与严格取消目标规则，不新增跨来源猜测。可从订阅列表按记录管理转换后的订阅；此登记不表示该上游限制已修复。

- **媒体库「继续观看」**：`GET /mediaserver/playing` 在 v2.15.6 已存在，参数 `server`/`count` 和 `MediaServerPlayItem` 字段（含可选 `percent`）与 v3 兼容；TV 媒体库页的「继续观看」行可直接使用。
- **搜索 SSE**：`/search/media/{mediaid}/stream`、`/search/title/stream` 及字幕流的事件类型仍是 `replace`/`heartbeat`/`error`/`done` 加 `items`、`stage`，TV 的 `SearchStreamEvent` 解码未变。
- **订阅**：`GET /subscribe/`、`GET /subscribe/media/{mediaid}`（含按标题回退）、`DELETE /subscribe/media/{mediaid}`、`PUT /subscribe/`、`POST /subscribe/`、`POST /subscribe/fork` 的公共可写字段与 v3 一致，`SubscribeShare` 也已有 `media_source`/`media_id`。v2 的 `PUT /subscribe/` 是整条替换（`to_public_write_payload()` 全量 dump，没有 v3 的 `exclude_unset`），TV 在 v2 上改为提交完整快照，避免只改一个字段却把站点、保存路径和过滤组清空；v2 也不会因身份变化清空进度，所以不弹「修改季或剧集组会重置进度」。
- **下载与整理**：`/download/`、`/download/subtitle`（v2 已接受 `media_source`/`media_id`）、`/history/transfer`、`/history/download` 的响应字段是 v3 的子集，TV 全部按可选字段解码。
- **插件来源的下载/字幕**：v2 的 `/download/add`、`/download/subtitle` 用 `Literal` 限定四个内置来源，插件来源或 `imdb`/`tvdb` 来源会被 422 拒绝；配套 Web 在 v2 上同样受限，TV 不额外兜底。
- **不进入 v2 的入口**：豆瓣短评/影评、共享媒体映射、应用内播放、单集试看、手动资源分页、reflink 整理都按已知起始版本门禁隐藏；v2 上取消订阅走媒体级 `DELETE`，不会误用 v3 的分页和映射能力。
- **主屏货架（Top Shelf）**：货架详情依赖成对媒体身份，v2 上不启用；设置页隐藏「主屏显示内容」，已保存的选择保留，换回 v3 后恢复。切服时 session 先于 settings 发布，货架只在设置确实属于当前账号时才用它判断版本，旧账号的设置不参与。
- **降级项**：`/media/source` 目录在 v2 不存在，TV 直接跳过请求，来源选择器保留内置来源；`/mediaserver/exists` 只能按 TMDB ID 或标题判断，v2 用 `success` 表示命中，TV 把未入库当正常结果，不再报错；响应没有 `server` 字段，多服务器配置下无法确认条目归属；插件来源的媒体身份在 v2 没有成对参数，详情靠标题/年份名称识别兜底，仍识别不到才返回空详情，订阅查询退回标题匹配。
- **版本读取失败**：`BACKEND_VERSION` 缺失或无法解析时，读请求以 v3 形状为主，并启用 v2 读兜底：详情额外带 `title`/`year`（v3 忽略这两个参数），`/mediaserver/exists` 把 v2 的 `success=false` 解释为未入库；`/media/search`、`/media/recognize` 仍使用 v3 的 `media_source`，实际为 v2 时这两项要等版本到达后恢复。兜底也意味着未解析且实际为 v3 时，`success=false` 会按未入库而不是错误处理。订阅写回直接拒绝：v2 的 `PUT /subscribe/` 是整条替换，v3 只写提交字段；版本未知时猜哪种都会改坏数据（猜 v2 会把编辑器里的旧草稿整条写回，猜 v3 会清空 v2 的站点和保存路径），所以 `APIService.saveSubscription` 由 `UnresolvedBackendEndpoints.subscriptionUpdateBody` 抛 `backendVersionUnavailable`，不发请求，订阅编辑页提示「正在读取后端版本，请稍后重试」。`fetchSettings` 在 `/system/global` 解码成功后、合并 `/system/global/user` 之前就应用版本，因此基础设置一到，保存和后续搜索已按正确协议执行；只有基础设置本身失败或超时才进入拒绝路径。已知 v2 仍提交完整快照，但不再额外发送 v3 的 `media_category_id`；v2 的整条替换语义保留，服务端目标在编辑期间被别的客户端改动时，后保存者仍会覆盖整条记录，与 Web v2 的行为一致。
- **验证边界**：契约部分为源码对照，没有可用的 v2.15.6 真实后端。已在 tvOS 27.2 Simulator 上完成单版本构建与定向测试，本轮共 240 个用例 0 失败：`SystemVersionInfoTests` 10 个、`MoviePilotV2EndpointsTests` 9 个、`TopShelfManagerTests` 30 个、`APIServiceCompatibilityEndpointTests` 50 个、`SubscribeSheetViewModelTests` 77 个（以上 176 个，后两个套件同时覆盖 v3 回归与 v2 门禁）；`SubscriptionWriteDTOTests` 15 个、`SubscribeModelCompatibilityTests` 9 个，共 24 个；合并主分支后的 `ContinueWatchingDisplayTests`、`HomeContinueWatchingRowTests` 共 40 个。完整套件、三版本矩阵和真实后端兼容测试未跑。

### 删除 v2 支持

1. 删除目录 `MoviePilot-TV/Services/BackendProtocol/MoviePilotV2/`（含 `UnresolvedBackendEndpoints` 和全量快照写回）。
2. 把 `BackendEndpoints.resolve` 的函数体改成 `return V3BackendEndpoints()`，并删掉未知版本的 `UnresolvedBackendEndpoints` 分支；把 `APIService.backendEndpoints` 的初始值改成 `V3BackendEndpoints()`。
3. 删除 `TopShelfManager` 的 `isAvailableForCurrentBackend`、`settingsProfileKey`、`currentSessionSettings`、`updateBackendAvailability(backendVersion:)` 和相关 guard（含设置回调传入新版本的那处），把 `SystemView` 恢复成 `if canConfigureRecommendations { topShelfSettings }`。
4. 删除登记表的 `v2.15.6` 行、README「MoviePilot 版本」段落里的 v2 说明和徽标中的 `v2.15.6 --` 前缀、本文件「不按版本复制接口」下方的 v2 例外条款与本节的表格/小节，`.agents/prompts/release.md` 和 `docs/subscription-compatibility-checklist.md` 里的 v2 下限，以及 `SystemVersionInfoTests`/`MoviePilotV2EndpointsTests` 里的 v2 断言。

`APIService` 只调用协议能力位（`supportsMediaSourceCatalog`、`mediaServerExistsHitIsSuccessFlag`、`includesDetailTitleFallback`），删掉 v2 实现后自动走 v3 的默认值，不需要逐处清理。

## 跟进一个新版本

1. 取目标后端标签和它 `version.py` 里的配套 Web 版本，与上一个登记版本对比差异。
2. 判断差异是否影响 TV 实际用到的接口、字段和写回。没有影响，就在登记表里加上这个精确版本，并在上表补一行；有影响，先适配再登记。
3. 同步 README 的版本说明和 `SystemVersionInfoTests` 中的登记表断言，运行仓库的模拟器构建和测试。
